## 1. Issue summary

The migration (commit `d5ba8ea`) passed its own test suite and descriptor diff but failed independent adversarial review. The review's empirical method (boot both modules, probe beyond the 13-capture harness) surfaced what the parity harness could not: a broken release path, a runtime/descriptor contract mismatch on the tenant lifecycle, 64-bit narrowing in generated DTOs, an incomplete listing-filter engine, seeding that ignores `loadReference`, two unsafe caches, a fail-open rehearsal harness, and spec/traceability overclaims. Separately, human review questioned conformance to the FOLIO API-first convention and the dual-scenario DB-object requirement.

The project's own cardinal lesson (M4: source-reading lies, only booted probing tells the truth) was validated a second time — the review found every one of its refutations by running things. The remediation plan therefore requires **each workstream to begin by reproducing its finding and to end with a regression test pinning the fix**.

## 3. Assessment of human-reviewer issue 2 — dual-scenario DB-object management

### Finding: both scenarios are already implemented through the standard folio-spring-support machinery; three review findings are the real gaps

How folio-spring-support supports it (verified in the library source, `folio-spring-base`):
- `FolioSpringLiquibase.performLiquibaseUpdate()` runs `CREATE SCHEMA IF NOT EXISTS <tenant_module>` and then executes the module changelog with that schema as default — per tenant, at `POST /_/tenant` time, never at application startup (`afterPropertiesSet` is suppressed).
- `TenantService.createOrUpdateTenant()` orchestrates it (synchronized; `beforeTenantUpdate → liquibase → afterTenantUpdate`); `deleteTenant()` drops schema + role on purge.
- `TenantController.postTenant` conditionally calls `tenantService.loadReferenceData()` / `loadSampleData()` when the `loadReference` / `loadSample` tenant parameters are `"true"`.
- Both reference modules use exactly this: a thin `TenantService` subclass + `FolioSpringLiquibase` + a Liquibase changelog under `src/main/resources/…changelog…`, `ddl-auto: none`, `_tenant` interface **2.0** in the descriptor, folio-spring's default (or trivially subclassed) tenant controller.

The port does the same (`ServintTenantService extends TenantService` with `FolioSpringLiquibase`; `changelog-master.xml` + 5 adoption files; `ddl-auto: none`), **plus** the adoption twist the reference modules don't need: every DDL changeset carries `preConditions onFail="MARK_RAN"` on `tableExists`, so:
- **Scenario 1 (existing tenants):** all 14 changesets MARK_RAN, zero DDL executed, legacy data untouched — empirically confirmed by the review (C2 body, F-10 note: only Liquibase's own bookkeeping tables are added, which the review's SRE lane classified operationally benign).
- **Scenario 2 (fresh deployments/tenants):** the same changesets execute fully and produce legacy-identical DDL — confirmed by the review modulo two deltas (F-10: a stray `DEFAULT false` and a column ordinal).

**Remaining gaps against the reviewer's "seamlessly" bar — all already captured as review findings, remediated below:**
- F-02: the descriptor declares `_tenant` 1.2 (legacy routes) but folio-spring implements the 2.0 contract → R2.
- F-06: seeding runs unconditionally in `afterTenantUpdate` instead of the `loadReferenceData()`/`loadSampleData()` overrides the framework invokes conditionally → R4.
- F-10: fresh-DDL `DEFAULT false` delta; C2/C3 claim wording → R9.

## 5. Recommended approach

**Direct adjustment** — add remediation workstreams as milestone M6; no rollback of completed work, no scope reduction. Rationale: the review confirmed the architectural core (descriptor parity C5, suite C8, legacy untouched C11, storage-level rollback compatibility, seed-content identity under flags); the refuted claims trace to enumerable, independently fixable defects. Rollback would discard a sound foundation; scope reduction is impossible against a wire-compatibility mandate.

Two governed **decisions** are embedded (each becomes an ADR through an SDD session):

1. **D-A: adopt `_tenant` 2.0** (drop the 1.2 parity attempt). folio-spring implements only the 2.0 contract; both reference modules declare 2.0; the tenant interface's sole consumer is Okapi, which drives enable/disable/purge from the *installed* descriptor — so after cutover the 2.0 routes are the ones called, and 1.2 parity has no consumer. Re-implementing 1.2 on Spring against framework grain is the strictly worse option. Consequence: ModuleDescriptor deviation from the legacy `_tenant` block, documented as a deliberate dossier entry (this is the review's D-17, resolved by decision rather than by code mimicry).
2. **D-B: keep `specs/api/` as the OpenAPI source of truth** (documented deviation from the `swagger.api` folder convention), unless the maintainers hard-require the conventional path, in which case the build-time sync copy is the fallback. The *approach* (generation) is identical either way.

## 6. Workstreams

Every workstream: (1) starts by re-reproducing its finding, (2) lands code + spec changes (spec changes via governed SDD sessions), (3) ends with a regression IT and, where applicable, a dossier entry. Efforts are focused dev-days.

### Phase 1 — Blockers

**R1 — Release path (F-01) — 2.5 d**
Replace root `Dockerfile` (Java 21 JRE base, `COPY target/mod-service-interaction-*.jar`, port 8081); convert Jenkinsfile + GitHub workflows (`run-int-tests`, `validate-module`, SBOM) to the Maven build at repo root; fix `DeploymentDescriptor-template.json` artifact name and port wiring (`server.port` from env, aligned descriptor `%p`); make CI build **and boot** the image. Acceptance: CI green building the port image; container answers `/admin/health` (or equivalent) on the descriptor's port.

**R2 — Tenant lifecycle to `_tenant` 2.0 (F-02 / D-17; decision D-A) — 1.5 d**
SDD sessions: ADR for D-A; `servint-tenant.yaml` rewritten to the 2.0 contract (incl. F-13's `204` fix); REQ-020 ACs updated. Code: descriptor `_tenant` block → 2.0 (`POST /_/tenant`, `GET/DELETE /_/tenant/{operationId}`); verify purge path (`purge=true`, blank `module_to` → schema+role drop) and disable path (schema retained) with new lifecycle ITs; bump folio-spring-base to released 10.0.0. Dossier: D-17 entry documenting the deliberate interface upgrade. Acceptance: every route the descriptor declares behaves as declared, proven by ITs.

**R3 — 64-bit number values (F-03) — 1 d**
SDD session: `format: int64` on `nextValue`, `maximumNumber` (and any sibling numeric fields audited against entity `Long`s) in the numgen spec. Regenerate (DTOs become `Long`), delete the `intValue()` narrowings from the mapper, add boundary ITs: POST/GET at `2147483648` / `4294967296`, adopted-row wire readback, legacy-write → port-read. Acceptance: review's exact probes pass; values survive round-trip unwrapped. *(Also serves as the live demonstration for reviewer issue 1 that spec-first generation is operating.)*

### Phase 2 — Behavioral parity

**R4 — Seeding semantics (F-06; issue 2) — 1.5 d**
Move refdata/number-generator/dashboard-access seeding into a `loadReferenceData()` override and widget-type import into `loadSampleData()` (framework invokes them conditionally — the exact folio-spring-support pattern the reviewer pointed at). Empirically re-derive the legacy **no-parameter** baseline (review measured 2 categories / 6 values / 0 generators — likely web-toolkit `@Defaults` on-first-access seeding, not tenant-enable seeding) and replicate its trigger, not just its content. SDD session: REQ-019 ACs per real trigger semantics; TRC-019 correction. ITs: parameters omitted / `true` / `false` × fresh / adopted schema. Acceptance: enable-matrix counts match legacy exactly.

**R5 — Listing engine: legacy kiwt grammar (F-04, shared with F-14) — 4 d**
Extend `KiwtListing` from `==`/`!=` to the legacy web-toolkit grammar: comparisons (`>`, `<`, `>=`, `<=`), case-insensitive eq, contains, null/not-null, value sets/ranges, grouping, negation, `&&`/`||` compounds; legacy-identical paging semantics (`perPage=0`, over-max behavior, defaults) and error tolerance (bad sort → 200, legacy-shaped envelopes). SDD session: behavior scenarios for the operator/paging matrix. ITs: side-by-side matrix transcribed from the review's probes (`nextValue>5`, `perPage=0/101`, bad sort). Acceptance: matrix byte-parity (or registered deviation with consumer evidence) on every probed case.

**R6 — First-use generation concurrency (F-05) — 0.5 d**
Atomic sequence initialization: `INSERT … ON CONFLICT DO NOTHING` then pessimistic-locked re-read (single retry loop); preserve the always-200 envelope. IT: repeated parallel fresh-pair generation (review reproduced 1-in-1 failure per race; test runs ≥5 rounds). Acceptance: no uniqueness-violation surfaces to the wire.

**R7 — Fresh-DDL parity + claim corrections (F-10) — 0.5 d**
Drop `DEFAULT false` from `refdata_category.internal` in the adoption changelog (legacy has none; seed/insert paths must set it explicitly); record the column-ordinal delta as benign in the dossier. Rewrite the runbook/docs C2/C3 assertions to "business tables/constraints/rows unchanged; Liquibase bookkeeping tables expected" with the corrected verification SQL. Acceptance: fresh-vs-legacy catalog diff empty modulo documented ordinal.

### Phase 3 — Security & robustness

**R8 — Caches, key lifecycle, display-data identity (F-07, F-08, F-09) — 2 d**

**R9 — Error-envelope and parameter-handling matrix (F-14) — 1 d, after R5**
